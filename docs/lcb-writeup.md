# 长程一致性怎么测：一个能自动判定的基准（LCB）

> 草稿 v1 · 2026-09-26。可发知乎 / 掘金 / 公众号 / GitHub Discussions。
> 配套代码：`bench/`（判定器 + 合成宇宙 + MCP server），`docs/BENCH_PLAN.md`（实施计划）。

---

## 一、问题：长程一致性是 agent 的真问题，但没有好尺子

让模型写一部 12 章的小说，它会干这些事：

- 第 2 章死掉的角色，第 4 章又端着水走过来
- 第 5 章才该知道的事，第 3 章就说了出来
- 第 1 章埋的细节（一道疤、一笔债），第 10 章回收时对不上

这些不是文笔问题，是**长程状态追踪**问题——和 agent 的记忆、上下文腐坏、知识边界是同一类。区别在于：代码任务有测试（SWE-bench），小说没有。

没有判定器，就只剩人工读稿——不可规模化，也不叫基准。

所以我做了 **LCB（Long-horizon Consistency Bench）**：一个**有自动判定器**的长程叙事一致性基准。它的定位不是「评测小说写得好不好」（那需要审美判断），而是**只测能自动判定的那部分**——状态、知识、时间线、约束。审美留给人类，状态留给机器。

## 二、设计五原则

| 原则 | 具体含义 |
|---|---|
| **自动判定** | 人手不进场。否则不可规模化，也不算基准 |
| **可复现** | 种子 / 模型版本 / 判定器版本 / judge prompt 版本全部入 manifest，任何数字可追到一次运行 |
| **可归因** | 同一模型跑「裸 harness vs 满 harness」，把**模型能力**与**工程 harness**分开 |
| **抗刷分** | 基准自带攻击自测（注水 / 重复 / 术语轰炸），并公示结果 |
| **离线可测** | 判定器核心纯函数化，单元测试**零 LLM、零网络**；LLM 判定走可注入后端 |

最后一条尤其重要：一个评测项目如果自己的判定器不可测，就没有资格评测别人。

## 三、测什么：四类可判定探针

| 类型 | 埋法 | 判定方式 |
|---|---|---|
| **知识边界** | 真相表标「谁在第几章知道什么」 | 角色提到此刻不该知道的信息 |
| **状态一致** | 死亡 / 物品 / 位置 / 时间线入状态账本 | 死人复活、物品瞬移、天数倒流 |
| **上下文腐坏** | 第 1 章埋无关细节 | 第 N 章能否正确回收，按距离画衰减曲线 |
| **约束遵守** | 禁词 / 篇幅 / 人称 / POV | 机械可数 |

知识边界是这套基准的护城河：要测它，你得先有「真相 / 知识」两层建模（作者维护权威事实表，逐角色维护已知集合）。多数自建评测没有这一层。

## 四、判定器：机械优先，清单式 LLM 兜底

**第一层：机械判定（确定性、免费、可审计）**

禁词计数、段落长度、篇幅偏差、POV 越界、人称混用、死人复活、时间倒流、物品双持有——这些都能用纯函数判定，零 LLM 调用，单元测试可精确断言。

**第二层：清单式 LLM 判定（只跑语义部分）**

知识边界这种需要理解语义的，不让 judge 自由打分，而是把「该角色此刻的已知集合」变成 **checklist 逐项判定是/否**。清单式判定的一致性远高于自由评分——这也是业界主流（Arena-Hard v2 / WildBench 一系）的做法。

**准入门槛**：judge 与人工标注的一致率（Kappa）达标才发版。judge 模型版本 + prompt 版本入 manifest。

## 五、归因：harness 三档消融

同一模型，跑三档：

```
bare   一个系统 prompt + 本章 spec              → 模型裸能力
mid    + 设定/状态/前文/知识边界注入             → 上下文工程的贡献
full   + 门禁 + 自动返修 + 状态回写              → 后处理门禁的贡献
```

为什么必须三档而不是两档：**门禁会字面上把违反改掉**（自动替换禁词、返修篇幅）。只跑「裸 vs 满」，你分不清改进是「上下文给对了」还是「门禁擦掉了」。三档让两者各领各的功劳——这就是 JD 里常说的「归因到模型能力 vs 工程 harness」。

## 六、合成宇宙：确定性 ground truth

基准的输入不能靠人写（那就不可规模化，也会有版权问题）。所以：

```
seed → 一部可跑的合成小说包
        cast + 真相表（含 false 行=错误认识）+ 知识表（谁在第几章学到什么）
        + 分幕 + 章节 spec（含声明式状态：谁死、谁拿到什么）
```

**关键决策：生成器零 LLM，纯确定性。** 同 seed 落盘文件**逐字节相同**。理由有两个：

1. 判定器需要 spec 结构精确可控
2. 基准的 ground truth 不能有随机性——否则「违反」的判定本身就不稳定

生成器还自带**不变量自检**：事实引用存在、学习章号在范围内、终局真相不早于末章、**死者不得在死后获知信息或作为行动者出现**、至少一条 held-out 事实、每章恰一个 expanded 节、时间线单调。

## 七、自证：判定器抓出的第一批违规，来自我自己的数据

这是我最想讲的一段。

写完判定器后，我把它们包成 MCP server，接进 Claude Code 真跑了一遍完整流程（生成宇宙 → 查账本 → 查真相表 → 跑门禁）。

**结果：账本显示某个角色第 2 章死了，可第 3-6 章的「在场名单」里还有他。**

原因是我的**生成器**：每章描述模板都会提一句这个名字（「某某以前也问过同样的问题」），而账本把「名字出现」记为「在场」——于是我的 ground truth 自相矛盾。

第二个 bug 是同一轮抓出来的：章节描述里硬编码了「她」，而该 seed 的主角是男性。

两个 bug 都不是单元测试能发现的——**单测只能覆盖我预设的行为**，而「死后点名」「人称与配置一致」这种跨章节约束，得真跑一遍链路才暴露。

我做了两件事：
1. 修生成器（死后章节改用其他角色；人称按角色性别取）
2. **把这一类加进不变量自检**：死者不得在死后章节描述中被点名——并配了**阴性对照测试**（人为注入一次违规，断言必须被抓到）

阴性对照是防自欺的关键：不变量如果恒返回「无违规」，测试照样绿，但什么都没测到。

（顺带一提：这也是为什么我坚持工具要被**真用一次**。设计文档、单测、demo 都替代不了真实链路。）

## 八、抗刷分：基准要自曝攻击结果

任何自动判定都会被针对性优化。所以基准自带三个攻击自测，且**结果公开**：

| 攻击 | 期望行为 |
|---|---|
| **注水**：同章拉长 2×（内容不变） | 分数**不变**（治长度偏差） |
| **重复**：复制段落 | 分数**下降** |
| **术语轰炸**：堆砌设定词但无实质 | 分数**不应上升** |

三条任一失败，说明判定器有偏，回头修。多数自建 benchmark 不敢做这件事——把攻击结果公开，等于自己给自己找麻烦。

## 九、实测数字（早期，样本很小）

拿真实写作文本对比（人类定稿 vs AI 草稿，同一部作品的相邻章）：

| 样本 | 字数 | 违反 | 每万字违反率 |
|---|---|---|---|
| 人类定稿（作者手改后） | 3518 | 1 | **2.8** |
| AI 草稿（未经修订） | 5803 | 16 | **27.6** |

差一个量级，方向符合预期。

**诚实标注**：这不是受控对照——两章不同模型、不同状态。受控对照要等三档 harness 跑批（W7/W8）。这里只能说：指标有区分度。

## 十、边界与诚实清单

- **合成宇宙 ≠ 真实长篇**：合成数据干净、可控，但缺少真实创作里的长尾混乱。计划附真实内容包做 in-the-wild 补充集
- **LLM judge 不可靠**：所以机械层优先 + 清单式判定 + Kappa 准入 + 判定器开源可审
- **规模还很小**：目前判定器 + 合成宇宙 + 协议入口完成，跑批/指标/榜单/抗刷分实验在实施中（见 `docs/BENCH_PLAN.md` 的 W7-W10）
- **不测审美**：写得好不好、有没有让人读下去的欲望，框架不碰——那是作者的事

## 十一、自己跑一遍（全离线，零 token）

```bash
git clone git@github.com:wanqili857-byte/fictionforge.git
cd fictionforge && git checkout feat/lcb-bench

# 生成一个合成宇宙（确定性）
python3 -c "
import sys; sys.path.insert(0,'.')
from bench.universe.generator import generate, write_universe
write_universe(generate(seed=99, chapters=6), '/tmp/u')"

# 查账本 / 跑门禁
python3 tests/test_universe.py    # 31 项
python3 tests/test_ledger.py      # 44 项
python3 tests/test_mechanical.py  # 30 项
```

接进 agent（MCP）：

```bash
claude mcp add lcb -- /path/to/fictionforge/.venv/bin/python \
    /path/to/fictionforge/scripts/lcb_mcp.py
```

然后直接说：「生成 seed 99 的六章宇宙，查账本看谁死了，再拿一段含死者的正文跑门禁」——工具会串起来跑。

## 十二、下一步

1. **跑批与指标**：三档 harness × 多模型 × k 次重复 → 第一张「模型 × 一致性」表
2. **知识边界判定**：探针生成 + 清单式 judge + Kappa 校准
3. **抗刷分实验**：三个攻击的实际数据
4. **榜单与复现协议**：让第三方能提交自己的模型

一句话总结这个项目的立场：**把「无法自动判定」的部分诚实地排除掉，把能判定的部分做成可复现、可归因、抗刷分的尺子**——然后先拿它量自己。
